\paragraph*{Two entry points.}
A user may start from a source artifact---a machine (\texttt{.mch}), refinement
(\texttt{.ref}), implementation (\texttt{.imp}), or system (\texttt{.sys})---in which case
\barrel{} invokes Atelier~B's \texttt{bxml} and \texttt{pog} programs and caches their
output.
Alternatively, an existing proof obligation file may be imported directly, which skips the
external programs altogether; this matters for reproducible builds and for corpora such as
the one used in \Cref{sec:benchmark-corpus}, where only the obligations are distributed.
Atelier~B's generator accepts a flag that additionally emits well-definedness obligations,
and \barrel{} does not pass it, preferring to regenerate those conditions itself for the
reasons given in \Cref{subsec:barrel-own-wd}.

\paragraph*{The two commands.}
The complete surface syntax consists of two commands, illustrated in
\Cref{lst:barrel-workflow}.
The command \leaninl{import $k$ $n$ from $d$} imports the artifact named \(n\) from
directory \(d\), where the kind \(k\) is one of \leaninl{machine}, \leaninl{refinement},
\leaninl{implementation}, \leaninl{system}, or \leaninl{pog}.
The command \leaninl{prove_obligations_of $n$} then reopens the obligations of \(n\)
that automation did not close, one per \leaninl{next} block.

\begin{leanlisting}[title={Importing and proving a B refinement chain.},
    label={lst:barrel-workflow}, float=t]
import Barrel

set_option barrel.atelierb "/path/to/atelierb"
open B.Builtins

import machine    MinSearch    from "specs/case_study"
import refinement MinSearch_r1 from "specs/case_study"
import refinement MinSearch_r2 from "specs/case_study"

prove_obligations_of MinSearch
next
  -- proof of the first obligation left open by the automation
  ...
\end{leanlisting}

Each \leaninl{next} block is paired, in order, with one proposition that the default
automation did not discharge.
Providing too few blocks, or too many, is an error; in the first case the obligations left
without a block stay open.
Every accepted block adds a named theorem to the environment
(\Cref{subsec:barrel-reification}), so a proof remains traceable to its source operation
and obligation family.
Because these are ordinary declarations, they can be reused as lemmas in later proofs,
inspected with Lean's dependency tools, and audited with \leaninl{#print axioms}.

\paragraph*{The three difficulties.}
Three difficulties stand between a proof-obligation file and a Lean theorem.
The statement has to be reconstructed: the file records types, definitions, variables,
hypotheses, and conclusions separately, and they have to be assembled into a single
proposition of the form \(\forall \vec{v},\, H_1 \impB \dots \impB H_n \impB G\)
(\Cref{subsec:barrel-normalization}).
That proposition has to be expressed in a logic where partial operators are fully applied,
which is where definedness evidence must be produced and where most of the design lies
(\Cref{sec:barrel-wd,subsec:barrel-reification}).
And the propositions have to be proved, or else presented in a form in which a user can
prove them (\Cref{subsec:barrel-automation,sec:barrel-interface}).
This is the order in which the difficulties arise, not the tool's own division into
components.
